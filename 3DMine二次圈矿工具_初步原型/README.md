## 一、快速开始

### 1. 环境要求



* Python 3.10+；Windows 需安装 **Access 数据库引擎**（pyodbc 直读 mdb）

* 依赖：`numpy`、`pandas`、`scipy`、`matplotlib`、`shapely`、`ezdxf`、`pyodbc`、`xlrd`、`openpyxl`



```
pip install numpy pandas scipy matplotlib shapely ezdxf pyodbc xlrd openpyxl
```

### 2. 一键运行

**直接读取 3DMine mdb 数据库**（定位表 + 测斜表 + pit\_blast 品位表，直孔）：



```
python main.py --csv "D:\...\北部山头3940平台-0915\2、3940平台炮孔数据库0915.mdb"
```

或运行模拟数据（演示 4 档齐全场景）：



```
python main.py --csv sample_data/blast_BL2026-015.csv
```



* 默认 `--method voronoi`：4 个品位等级（0.5-1 / 1-1.5 / 1.5-3 / ≥3 g/t）分别圈矿，Voronoi 单元面积加权计算矿量与品位，叠加 1m 网格并输出 CAD（DXF），DXF 上标注矿块号。

* **按平台 / 日期分组**：mdb 按工程号前缀解析平台与日期，每个平台每天单独圈连、单独出图出表（对应人工逐平台逐日处理）。

真实 0915 运行输出（节选）：



```

[分级] 0.5-1.0 g/t: 1 个泰森单元，废石单元 1 个
[分级] 1.0-1.5 g/t: 24 个泰森单元

[输出] CAD DXF：3940平台 0915二次圈矿矿块图.dxf
[报告] 炮孔数据报告（xlsx+csv）...
```

### 3. 结果加载到 3DMine / CAD



* **3DMine**：`文件 → 导入 → 字符串(.str)`，选择 `output/BS-{平台}-{日期}_L{1..4}_grade.str`（4 个品位等级各一个文件，UTF-8 无 BOM、逗号分隔、带真实坐标闭合多段线）。

* **CAD**：AutoCAD / 浩辰 / 中望打开 `output/{平台}平台 {日期}二次圈矿矿块图.dxf`（R2010，单位米 INSUNITS=6）。等级界线按图层分色、体号标注、1m 网格独立图层。

* **报告**：`output/{平台}平台 {日期}炮孔数据报告.xlsx` 与人工 Excel 报告同版式；`矿块汇总（粘贴CAD）.txt` 可直接复制到 CAD 图。

## 三、处理流程（对应人工流程与计划书）



| 步骤 | 内容                                                                                           | 对应人工流程 / 计划书              |
| -- | -------------------------------------------------------------------------------------------- | ------------------------- |
| 1  | **数据源**：直读 3DMine mdb（定位表 = 孔口坐标，测斜表 = 直孔，pit\_blast = 品位），或同字段 CSV；按平台 + 日期分组               | 人工导入 Excel→mdb；§4.1、§12.7 |
| 2  | 台阶品位合成（直孔按孔口坐标；品位取 pit\_blast 单段值，每孔一条品位记录）                                                  | 人工 blast list             |
| 3  | **Voronoi 分级圈矿**：每孔泰森单元（爆区边界 = 孔位凸包外扩 3m），按 4 个品位等级分类                                        | 人工按炮孔显示品位圈连；§5.2          |
| 4  | **矿块合并**：同等级相邻单元并集成候选矿块；滤除小于 `min_ore_area_m2` 的孤立小块                                         | 人工手动圈连                    |
| 5  | **品位归并（单一品位）**：矿块内混入的低品位炮孔（如 1-1.5 块中的 0.89 孔）并入邻接高档块，**平均品位 = 金属量 / 矿石量**，矿块档位 = 加权平均品位所在区间 | 用户规则：不同品位累加后金属量 ÷ 矿石量     |
| 6  | **1m 网格**：每个矿块生成边长 1m 的正方形网格线裁剪到块内                                                           | 人工加炮孔网格图（边长 1）            |
| 7  | **CAD 输出**：4 档矿界线分图层闭合多段线 + 网格 + **体号标注** + 标题，带真实坐标                                         | 人工在 CAD 中标矿块号             |
| 8  | **炮孔数据报告**：与人工 Excel 同版式（类型 / 体号 / 体积 / 重量 / 平均品位 / 金属量百克 + 小计 / 合计）                         | 人工 Excel 汇总报告             |
| 9  | 4 档 .str 界线文件 + 矿块 - 炮孔明细 + 可粘贴 CAD 汇总文本 + 验证图                                               | 人工报告 + 图                  |

## 六、矿块品位归并规则（复现人工流程）

人工流程中，圈连出的一个矿块内可能混有不同品位类型的炮孔（如一个区域有 5 个 1-1.5 g/t 孔 + 1 个 0.89 g/t 孔）。工具自动复现：



1. 按 4 个品位等级分别圈出候选矿块（同等级相邻泰森单元合并）；

2. **跨档归并**：低品位矿块若**质心落在高档矿块内部**（即矿块内混入的低品位孔）、面积占比 ≤ 50%、且并入后加权平均品位仍 ≥ 高档档位下限，则并入该高档矿块；

3. **平均品位 = 金属量 / 矿石量**（品位 × 面积加权），矿块档位 = 加权平均品位所在区间；

4. 归并后每矿块只有一种品位档，体号全局唯一并标注在 CAD 图与验证图上。

> 贴边（仅共享边界）的低品位块
>
> **不**
>
> 并入、独立成块 —— 与人工 0915 成果一致（0.5-1 档 1 孔单独成块）。

## 一、先给出总体评审结论

1. 数据处理、报告生成、CAD 自动绘图：可行性高

Excel 解析、分档统计、几何运算、DWG 绘制及报告填充，都可以通过 Python 实现。

2. 自动复现人工圈矿：可行，但需要样本反演和规则校准

单纯使用 DBSCAN、Alpha Shape 或品位加权，不能自动保证与人工矿块一致。需要建立可解释、可配置的合并规则，并使用已验收图件进行校准。

3. 矿量计算：必须先确定统一计算口径

Voronoi 分区、平台厚度、矿体边界和体重参数必须有明确的地质依据，不能仅凭算法输出就认定矿量正确。

4. 三件套自动交付：可行，但需要先验证文件兼容性

DXF/DWG 与 Excel 相对容易自动化；3DMine 对 .3ds 的具体导入方式、坐标和实体类型兼容性，需要在实际软件环境中验证。

我建议把项目的核心目标从“自动画出矿块”升级为：

输入相同的数据和参数，能够重复生成相同结果；每一个矿块都能追溯其炮孔来源、合并理由、品位计算过程和矿量计算过程；发现不符合人工规则的地方时，可以定位并修改。

这会比单纯追求一键出图更重要，因为它决定了工具能不能长期用于生产。

## 二、现有方案中，我认为最需要修改的 8 个地方

### 1. 不要把“聚类算法”直接当成“圈矿算法”

这是整个项目最关键的问题。

你目前设计的是：

> DBSCAN 初聚类 → 品位加权归位 → 强制合并 → 生成矿块。

这个顺序有一定合理性，但存在一个风险：空间上接近的炮孔，不一定属于同一个可采矿块；空间上略有间隔的炮孔，也可能因为矿体连续性和开采条件而需要合并。

例如：

* A、B 两组炮孔距离较近，但中间存在低品位隔离带或明确的地质边界。

* C、D 两组炮孔之间有一定间距，但它们处于同一连续矿化带，人工判断应当圈为一个矿块。

* 一组高品位孔周围存在低品位孔，单纯按加权平均品位归档，可能掩盖局部低品位区域。

建议把算法拆成三个独立阶段。

第一阶段：空间关系构建

孔位、距离、邻接关系、平台、地质约束

第二阶段：可采矿块识别

品位条件、连续性、孤立孔处理、人工合并规则

第三阶段：矿块边界与属性计算

边界构建、品位统计、矿量计算、质量检查

DBSCAN 可以保留，但建议把它作为候选空间分组工具，而不是最终圈矿决策器。

更适合生产使用的方式是构建炮孔邻接图：

* 每个炮孔作为一个节点。

* 满足距离、品位连续性等条件的炮孔之间建立连接。

* 根据规则决定哪些连接可以保留，哪些连接需要断开。

* 对剩余连接形成的连通区域进行矿块划分。

* 对人工指定的合并、拆分及例外情况进行显式记录。

这样既能利用自动化算法，也能保留地质人员的判断权。

### 2. 取消“孤立孔一律并入最近矿块”的无条件规则

原方案中这条规则需要修改。

如果孤立炮孔直接并入最近矿块，可能产生三类错误：

1. 把低品位炮孔错误并入高品位矿块。

2. 把不同矿化区域合并。

3. 让原本不满足可采条件的矿块被错误扩大。

建议改为条件式处理：

| 孤立孔情况            | 建议处理             |
| ---------------- | ---------------- |
| 距离近，品位差小，满足合并条件  | 自动合并             |
| 距离近，但品位档差异明显     | 按可采性规则判定         |
| 距离较远，缺乏连续性证据     | 暂不合并，列入待审核清单     |
| 低于 0.5 品位        | 只参与规定的统计，不进入圈矿流程 |
| 位于边界、坐标异常或存在重复记录 | 标记异常，优先人工核查      |

对于不能确定的炮孔，输出“待人工复核”比强行给出矿块归属更安全。

### 3. “同一簇只保留一个品位档位”必须区分两种概念

你的方案举例：

> 5 个 1.0–1.5 品位孔 + 1 个 0.89 品位孔，整体归为 1.0–1.5。

这个结果在某些人工规则下可能合理，但不能把它直接固化为通用算法。

因为至少要区分：

* 炮孔品位档位：每个炮孔自身所属的原始品位区间。

* 矿块品位档位：根据最终矿块的统计品位，按既定规则确定的档位。

这两者不应混为一谈。

例如，6 个炮孔的品位分别是 1.2、1.3、1.1、1.4、1.2、0.89，算术平均值为：

Gˉ=∑i=1nGin\bar G=\frac{\sum_{i=1}^{n}G_i}{n}Gˉ=n∑i=1nGi

得到的平均值约为 1.18，但如果各炮孔的代表体积不同，就不能直接使用算术平均值作为矿块最终品位。

建议程序同时保留：

* 原始炮孔品位及其档位；

* 矿块统计平均品位；

* 矿块最终归档档位；

* 归档所使用的规则编号；

* 归档前后品位与孔数变化。

矿块归档究竟采用算术平均、体积加权还是金属量加权，必须以实际生产统计口径为准，不能由开发人员自行决定。

### 4. 不要一开始就把 Alpha Shape 作为唯一边界算法

Alpha Shape 适合生成不规则边界，但参数选取会显著影响结果。

参数过小，矿块可能出现断裂、碎片或孔位遗漏；参数过大，边界会逐渐接近凸包，容易把空白区域也圈进去。

建议同时实现三种候选边界方式：

| 方法           | 优点             | 主要风险         | 建议用途            |
| ------------ | -------------- | ------------ | --------------- |
| Convex Hull  | 稳定、简单、易验证      | 边界偏外扩        | 基准结果、简单矿块       |
| Alpha Shape  | 能拟合不规则边界       | 参数敏感、可能产生碎片  | 不规则矿块           |
| Voronoi 单元并集 | 与炮孔分区和面积统计衔接方便 | 边界受邻接及裁剪条件影响 | 与 3DMine 计算口径对接 |

我更建议把 Voronoi 单元并集作为重点验证方案，Alpha Shape 作为候选方案，而不是提前指定某一种算法一定最接近人工圈矿。

还要注意：Voronoi 边界只有在明确了有效孔位、平台范围、矿块归属和边缘单元裁剪方式后，才适合用于矿量统计。不能把无限延伸的 Voronoi 区域直接当成矿块面积。

### 5. 将“圈矿结果”和“出图结果”彻底分离

这是工程实现层面非常重要的一项修改。

不要让程序一边判断矿块、一边直接往 CAD 中画线和写字。否则，调整一个矿块合并规则时，可能牵连全部绘图逻辑。

建议建立一个统一的中间数据模型，例如：

Python

运行

```
MineBlock = {
    "block_id": "B001",
    "platform": "3940",
    "date": "1004",
    "hole_ids": [],
    "grade": None,
    "grade_class": None,
    "boundary": [],
    "area_m2": None,
    "volume_m3": None,
    "tonnage_t": None,
    "metal_content": None,
    "rule_trace": []

```

这只是数据结构示意，实际开发时还应加入坐标系、单位、原始记录标识、计算版本、审核状态等字段。

然后采用统一的中间结果驱动三个输出：

* DWG：读取矿块边界、孔位、品位、标注和绘图样式。

* XLSX：读取矿块属性、分档汇总及计算结果。

* .3ds：读取经过校验的矿块几何数据，并通过验证后的转换接口导出。

这样即使以后从纯 Python 切换到 3DMine 计算，报告和绘图模块也不必全部重写。

### 6. 将“3DMine 优先”改为“先验证接口，再决定主计算引擎”

原方案优先使用 3DMine COM 或宏，是合理的，但这里存在一个需要提前验证的风险：不能预设当前安装的 3DMine 版本一定提供可直接调用的 COM 接口，也不能预设其全部功能都支持脚本自动化。

建议在开发第一周完成接口验证，重点检查：

* 能否通过宏、命令接口或其他自动化方式导入数据库；

* 能否可靠读取炮孔坐标、品位和相关属性；

* 能否调用 Voronoi 或对应的矿量计算功能；

* 能否获取计算结果，而不仅仅是执行界面操作；

* 能否自动导出指定格式的几何文件；

* 批量执行时是否存在弹窗、卡死、坐标精度或版本兼容问题。

如果某项功能不能可靠调用，就不要让整个系统依赖它。

更稳妥的策略是：

Python 负责数据清洗、规则管理、结果校验和文件编排；3DMine 负责已经验证可靠的专业几何或矿量计算；AutoCAD 负责必要的最终图件兼容性验证。

至于哪些计算放在 3DMine 中，哪些由 Python 完成，应以实际接口测试和人工对照结果决定。

### 7. DWG、Excel 和 .3ds 必须共享同一套矿块编号与计算结果

原方案已经注意到重复编号和漏标问题，但建议把检查提升为程序的硬性约束。

每个最终矿块应拥有一个稳定的唯一 ID，例如 `B001`、`B002`。同一 ID 必须贯穿：

* CAD 矿块边界；

* CAD 矿块编号引线；

* Excel 矿块明细；

* .3ds 几何对象或属性映射表；

* 程序运行日志。

不要仅仅依靠图上的“2号、3号”作为关联依据。

建议导出时进行双向核验：

| 核验项目           | 合格条件            |
| -------------- | --------------- |
| 矿块 ID          | 唯一、不为空          |
| 矿块编号与边界        | 一一对应            |
| 矿块编号与 Excel 明细 | 一一对应            |
| 矿块编号与 .3ds 对象  | 按约定的映射关系一一对应    |
| 炮孔归属           | 每个参与圈矿的炮孔符合归属规则 |
| 边界几何           | 闭合、有效、无非预期自交    |
| 统计合计           | 分项汇总与总计一致       |

此外，应把“图上标注数量”和“实际矿块数量”分开统计。即使两个数量相等，也不能证明每个矿块都标对了；还必须逐个检查 ID 对应关系。

### 8. “报告粘贴到 CAD”应作为独立输出模块

你要求在 DWG 中附带报告图片，这可以实现，但不建议把它与核心圈矿模块耦合。

更合理的流程是：

1. 先完成矿块图及全部标注。

2. 生成并检查 Excel 报告。

3. 将指定报告区域导出为清晰的图片或采用其他经验证的嵌入方式。

4. 统一插入 CAD 图框中的报告区域。

5. 检查图片是否丢失、文字是否清晰、打印比例是否合适。

如果报告区域包含大量小号中文，优先考虑可控的分辨率和打印效果；如果采用图片引用，还必须验证文件交付后不会出现外部引用丢失。

这个模块建议放在所有计算之前，检查不合格的数据不要直接进入圈矿程序。

重点检查以下情况：

| 检查项目       | 处理方式                  |
| ---------- | --------------------- |
| 炮孔编号重复     | 区分重复记录与合法的多条记录，禁止静默去重 |
| 孔位坐标缺失     | 隔离异常记录                |
| 品位为空或非数值   | 标记异常，不得直接按 0 处理       |

你目前设定全部按直孔处理，这可以作为当前项目的明确业务假设，但要增加验证条件：如果测斜数据表明实际存在明显偏斜孔，就应报警，而不是静默忽略。

另外，品位档位必须采用明确的左闭右开或右闭左开规则。例如，1.0、1.5、3.0 分别归属哪个档位，要统一规定，防止边界值在不同模块中被重复统计或遗漏。

### 3. 把矿量计算做成独立的可替换模块

建议把矿量计算定义为一个独立接口，而不是把公式散落在圈矿、报告和 CAD 模块中。

例如：

Python

运行

```
calculate_block(
    boundary,
    hole_data,
    thickness_model,
    density_model,
    calculation_method
)
```

这里有三个特别重要的技术问题。

第一，面积不等于体积。

如果采用统一厚度估算：

V=A×HV=A\times HV=A×H

其中 AAA 为矿块有效面积，HHH 为有依据的有效厚度或台阶高度。必须确认这个厚度确实适用于当前矿块，不能默认平台高度就等于矿体厚度。

第二，吨位必须使用有效体重参数。

T=V×ρT=V\times \rhoT=V×ρ

其中 ρ\rhoρ 为经确认的体重，单位应与体积、吨位统一。

第三，金属量和平均品位必须使用同一套矿量权重。

对于各单元吨位 TiT_iTi 和品位 GiG_iGi，加权平均品位可表示为：

Gˉ=∑iTiGi∑iTi\bar G=\frac{\sum_i T_iG_i}{\sum_i T_i}Gˉ=∑iTi∑iTiGi

如果品位单位是 g/t，金属量以 kg 计，则：

Mkg=∑iTiGi1000M_{\mathrm{kg}}=\frac{\sum_i T_iG_i}{1000}Mkg=1000∑iTiGi

上述公式以金矿品位为 g/t、吨位为 t 为前提；如果你的报告使用其他单位，必须相应转换。

这些公式只是计算框架。实际生产中的矿块有效面积、厚度、体重、边界裁剪、贫化损失以及低品位孔的处理方式，仍然必须与现行人工统计和 3DMine 计算口径逐项对齐。

### 4. 增加人工干预和结果锁定机制

我不建议第一版就追求完全无人审核。

更合理的是设置三种运行模式：

预览模式

只输出炮孔分组、候选矿块边界、疑似异常和待合并矿块，不生成正式成果。

人工复核模式

地质人员可以合并、拆分或调整矿块归属，并记录操作原因及修改前后的结果。

正式出图模式

只有通过规则检查和必要的人工审核后，才生成最终三件套，并记录审核状态。

如果后期经过足够多的人工案例验证，可以逐步扩大自动通过范围，但不应让算法在无法判断时悄悄作出地质决定。

还有一个容易被忽视的点：DXF/DWG 中的文字样式、中文字体、外部参照和栅格图像必须在最终使用的 AutoCAD 环境里检查。生成文件成功，不代表在其他电脑上打开和打印时一定正常。

## 六、最重要的验收建议：不要只比较图面是否相似

建议建立四级验收标准。

| 验收级别    | 检查内容           | 判断重点              |
| ------- | -------------- | ----------------- |
| L1 数据正确 | 炮孔数量、坐标、品位、分档  | 数据是否完整、是否误筛       |
| L2 计算正确 | 矿块归属、边界、品位、矿量  | 算法与人工规则、统计口径是否一致  |
| L3 图件正确 | 引线、网格、编号、图层、字体 | 图面是否完整、清晰、可打印     |
| L4 交付正确 | DWG、XLSX、.3ds  | 是否能打开、是否兼容、数据是否一致 |

### 建议重点增加的量化指标

* 炮孔归属一致率：自动结果与人工确认结果中，炮孔所属矿块一致的比例。

* 矿块匹配率：自动生成的矿块与人工矿块在一一匹配后的数量及匹配情况。

* 边界重合度：采用交并比（IoU）衡量自动边界与人工边界的几何重合程度。

* 品位和矿量误差：分别对照人工统计表和 3DMine 计算结果。

* 绘图完整率：应有矿块编号、引线、品位文字和边界的实际完成比例。

* 跨文件一致率：DWG、Excel 和 .3ds 中对应矿块的编号及属性是否一致。

这些指标需要先通过真实人工样本确定可接受阈值，不能随意规定一个比例就认定系统合格。

特别是矿块匹配，不宜只按编号比较。自动算法生成的 `B001` 不一定就是人工图中的 1 号矿块，应先按炮孔集合重合程度及边界重合程度匹配，再比较属性。

我建议设置一票否决项： 关键炮孔丢失、矿块编号重复、报告总计不一致、几何边界损坏、坐标系统错误、输出文件无法正常打开，任何一项出现都不应自动判定验收通过。

## 一、总体结论

**项目可行，建议立项，但应按"规则驱动的半自动圈矿系统"定位，而非"全自动圈矿黑箱"。**

理由分三层：

- **技术可行性：高。** 涉及的全部技术——Excel 解析、空间聚类、几何计算、DXF/DWG 生成、.3ds 导出——都是成熟技术，Python 生态（pandas、shapely、ezdxf 等）足以覆盖，无不可逾越的技术障碍。
- **算法可行性：有条件成立。** 自动复现人工圈矿不是算法问题，而是**规则工程问题**。只要有足够的已验收人工样本用于反演和校准规则，自动化复现是可以做到的；如果样本不足，则只能做到"辅助圈矿"。
- **落地可行性：取决于前置工作。** 当前最大的风险不在开发，而在**矿量计算口径、3DMine 接口能力、人工规则的显性化**三件事尚未验证。这三件事不解决，写出的程序无法通过生产验收。

因此结论是：**值得做，但必须先做"阶段 0"（数据与口径验证），再进入编码。**

### 1. 数据处理与报告生成 —— 可行性 ★★★★★

### 2. 空间圈矿算法 —— 可行性 ★★★☆☆（条件性）

| 环节 | 可行性判断 |
|---|---|
| 空间分组（DBSCAN/邻接图） | 高，但只能作候选分组，不能直接定矿块 |
| 矿块合并/拆分 | **中，是全项目核心难点**——需从人工案例中反演规则，且规则需可配置、可追溯 |

## 四、算法与规则的具体修改建议

### 1. Voronoi 可作基准，但不要唯一
建议同时保留三种边界方案做对比：
- 凸包：稳定，适合基准；
- Alpha Shape：拟合不规则边界，但参数敏感；
- Voronoi 单元并集：与矿量面积统计衔接最好。

当前 Voronoi 方案可以继续作为主方案，但必须做外扩距离、最小面积、边缘裁剪的敏感性分析。

### 2. 不要用 DBSCAN 直接定矿块
DBSCAN 只能做候选分组。更稳的是：
- 炮孔为节点；
- 满足距离、品位连续性、平台约束的孔建边；
- 按规则保留/断开连接；
- 连通区域作为候选矿块；
- 人工合并/拆分显式记录。

### 3. 品位归并必须保留三层信息
每个矿块至少记录：
- 原始炮孔品位及原始档位；
- 矿块统计平均品位；
- 矿块最终归档档位；
- 归档规则编号；
- 合并前后孔数、面积、品位变化。

平均品位必须用吨位加权：  
`G = Σ(T_i × G_i) / ΣT_i`  
如果同台阶同容重，面积加权可近似，但多台阶后必须吨位加权。

### 4. 孤立孔改为条件式处理
- 距离近、品位差小、满足合并条件 → 自动合并；
- 距离近但品位档差异明显 → 按可采性规则，输出待审核；
- 距离远、缺乏连续性 → 不合并，待审核；
- 废石 <0.5 → 只参与统计，不进入圈矿；
- 坐标异常、重复记录 → 标记异常，人工核查。

### 5. 体号：内部 UID 稳定，外部显示号可重排
建议：
- `block_uid`：稳定唯一，如 `3940-1004-B0007`；
- `display_no`：按高档在前全局连续；
- CAD、Excel、.str/.3ds、日志全部用 `block_uid` 关联；
- 显示号变化时，记录映射关系。

## 五、工程架构：所有输出必须同源

建议架构：

```
输入层：mdb / CSV / Excel / 人工参考图
数据质量层：字段映射、坐标统一、校验、分档、版本记录
计算核心：邻接图分组 → 规则合并/拆分 → 边界 → 矿量与品位
统一中间模型：MineBlock + Hole + Run
输出适配器：
  - DWG 2010 / DXF
  - XLSX 报告
  - .str / .3ds
  - PNG 验证图
  - 审计日志 / 验收报告
```

核心原则：**DWG、Excel、.3ds 不允许各自重新计算一遍矿块，必须读取同一份 MineBlock 数据。**

建议中间模型字段：
- `block_uid`, `display_no`, `platform`, `date`, `bench`
- `hole_ids`, `grade_class`, `grade_avg`
- `area_m2`, `volume_m3`, `tonnage_t`, `metal_content`
- `boundary_wkt`, `boundary_method`
- `params_version`, `rule_trace`, `review_status`
- `source_file_hash`, `program_version`

## 六、验收：不要只比图面相似，要四级验收

| 级别 | 检查内容 | 重点 |
|---|---|---|
| L1 数据正确 | 炮孔数、坐标、品位、分档 | 是否完整、是否误筛 |
| L2 计算正确 | 孔归属、边界、品位、矿量 | 与人工规则、统计口径是否一致 |
| L3 图件正确 | 引线、网格、编号、图层、字体 | 是否完整、清晰、可打印 |
| L4 交付正确 | DWG、XLSX、.str/.3ds | 能否打开、兼容、数据一致 |

建议量化指标，初值可参考：
- 炮孔归属一致率 ≥ 95%；
- 矿块匹配率 ≥ 90%；
- 边界 IoU ≥ 0.85；
- 体积/吨位误差 ≤ 3%；
- 平均品位误差 ≤ 2%；
- 金属量误差 ≤ 3%；
- 跨文件一致率 100%。

**一票否决项**：关键炮孔丢失、矿块编号重复、报告总计不一致、几何边界损坏、坐标系错误、输出文件无法打开。

## 七、最建议先做的事：阶段 0，而不是继续加功能

我建议下一步不要先做克里金、Web 界面或 3DMine 插件，而是先做“阶段 0”：

1. **固定基准案例**：以 `3940平台 1004` 或已有 0915 为首个基准，确认炮孔数据库、人工 DWG、人工 Excel 对应同一天同一平台。
2. **建立人工标准答案**：每个炮孔的原始品位、人工矿块归属、最终矿块档位、合并原因。
3. **冻结计算口径**：厚度、体重、分档边界、金属量单位、外扩、最小面积、归并规则。
4. **验证接口**：3DMine 对 .str/.3ds 的导入回读、COM/宏能力；AutoCAD 2010 对 DWG/DXF、中文字体、打印效果；Access 引擎部署。
5. **统一中间模型与稳定 UID**。
6. **跑 1004 与人工逐块对比**：按档、按块、按孔归因误差，而不是只看总量。
7. **增加异常清单和人工复核模式**。
8. **形成《详细开发规范与验收测试清单》**，再进入编码迭代。

## 八、结论

**项目值得继续，但应从“全自动圈矿黑箱”转为“规则驱动半自动圈矿系统”。**

现有 PoC 是很好的阶段 1 基础，不要推翻重写。下一步应优先补齐：
- 口径冻结；
- 规则配置化与版本化；
- 稳定 UID 与统一中间模型；
- 人工复核与异常清单；
- DWG/.3ds 接口验证；
- 四级验收与逐块误差归因。

最宝贵的建议一句话：  
**先把人工判断变成可验证规则，再把规则变成可追溯数据，最后才让 CAD、Excel、3DMine 去读同一份数据。**  
这样工具才能真正进生产，而不是停留在演示。
