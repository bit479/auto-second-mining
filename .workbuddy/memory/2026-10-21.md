## 损贫计算工具 v0.4：首页公式改成「单元格+单元格」

用户原话：「该损贫计算项目中首页计算公式太过复杂，能不能换成单元格＋单元格的形式」。
先给了三个方案（加小表 / 只填数值 / 逐级引用长链），用户选了**加「平台×品位」小表**。

### 做法（`core/excel_writer.py`）

三层加法，首页再无 SUMIF/SUMIFS/COUNTIF：

| 层 | 公式 |
|---|---|
| 小表每格 | `=C46+C53`（该平台该品位各报告的**小计**行相加；报告只有一个品位时用**合计**行）/ `=(F46+F53)/10` 转 kg |
| 小表合计行 | `=B26+B27+…+B37`（各平台相加） |
| 各平台行 | `=B14+E14+H14+K14`（4 个品位档相加），总计 `=C9+C10+…` |
| 分山头行 | `=C9+C10+C11+C12`（该山头各平台相加），合计 `=C3+C4` |
| 品位行 | `=B38`（直接引用小表合计行），体号写固定数字 |

- `_plan_cross(grid, platform_totals, dedup_result, grade_keys, fallback, span_ok)`
  是核心：按 (区域,平台,品位) 收集要加的**目标行号**，`_block_sources()` 决定用
  「小计行」还是「逐条数据行」（报告内有被剔除/待审的行、或小计跨多个品位 → 退回数据行）。
- 小表布局：1 列平台（写成 `北部山头3950`，因为 3930/3940 南北都有）+ 每档 3 列
  （体积/重量/金属量），共 `1+3n` 列；两行表头（档次合并 + 三个指标）。
- ⚠️ **引用明细数据必须用报告的 `col_map` 取列，不能用小表自己的列位**。
  我第一版直接用了小表的 B/C/D → 取到了明细的「体号/体积/重量」，数字全错。
  兜底 `_DETAIL_COLS = {volume:3, weight:4, metal:6}`。
- `/10` 必须写 `=(a+b+c)/10`，只写 `=a+b+c/10` 会把最后一项之外的都算错（踩过）。
- 小表横跨 G 列（原本是两块之间的窄分隔列，宽 6），有数据时 G 要改成 13，
  否则那一格被挤成竖排文字。

### 顺带挖出三个「重复计入」——**数字变了，必须告诉用户**

对着上库矿区 10 月真实数据核数时发现旧版把三类东西算了两遍，总量虚高约 3%：

1. **报告「合计」行下面的 `3DMine 炮孔数据库报告` 附表 = 同一批矿块的拆分**
   （主表 1101.775 → 附表 374.494 + 727.281，附表总计 = 主表那一行）。
   旧 parser 只在「连续 2 个空行」才停，于是把附表当数据又加了一遍。
   **改法：parser 遇到「合计/总计/汇总」行就 break**（「小计/平均」继续读）。
   附表行数记进 `ParsedReport.trailing_rows`，在「处理日志」注明未计入。
2. **`二次圈矿成果_xxx\` 导出副本**：`_walk` 命中即停是对的，但 `scan()` 用的是
   `find_reports(folder, recursive=True)`（`rglob`），副本照样被扫进来——
   日志写着"已忽略"、实际算了两遍。**改法：`scan()` 里这一层直接有报告就只认这一层。**
3. **`炮孔品位统计（孔数）` 附表**被当成数据行（体积格是 `1.5-3` 这种文字，
   体号计数也跟着虚高）。随第 1 条一起消失。

上库矿区 10 月对照（可作以后核数基准）：

| v0.3.1 | 398,624.989 | 1,074,528.819 | 1,050.033 | 188 |
| v0.4 | 386,210.106 | 1,040,953.034 | 1,006.946 | 177 |

## 损贫计算工具 v0.5：选日期 + 三处提示

用户："给程序加一个选择日期的功能，你的脚本有错账"，随后列了四条。
逐条核完，**只有两条是真问题，其余是他看旧输出的误判**（他跑的
`二次圈矿量合计_20261021_0922.xlsx` 其实是 v0.4，副本已经排除了）：

| 他的说法 | 实际情况 |
|---|---|
| 3950 1014 正本+副本算两次 | v0.4 已修；他那份 3950 = 161,357.05，副本 9,191 t 不在里面 |
| 副本混进「≥3：3 t」「0.5-1体5：76 t」 | 那是 `炮孔品位统计（孔数）` 两列小表；v0.4 起解析到合计就停，副本也不再扫描 |
| 4000 0920 计了 1,799 t | **确实计入了，但只一次**（0921 那份内容全同，被"完全重复"剔掉）。问题是标题写 0825 → 需人工判断要不要排除 |
| 3960 两笔待审被计入 | **他勾了「把待审数据也计入」**：3960 从 222,156 → 240,496（+18,340 t） |
| 4000 的 924-2 只有 .xls 没取到 | **整份数据 123 个 .xls 里没有一个含「类型/体号」表头**；4000-0924 目录里只有 `炮孔数据库.xls`（定位表/测斜表/pit_blast），没有报告，3,758 t 不在这个目录里 |

### 实现

- `scanner.day_inventory(root)` 出「日期/文件夹/报告数」清单；
  `day_aliases()` 支持 `0924` / `2026-09-24` / 文件夹全名（`0924` 命中所有平台的 0924）；
  `scan(dates=...)` 过滤；`mmdd_from_text()` 取**最后一个**"像月日"的 4 位数
  （`4000平台 0825…` → 0825，不能把 4000 当日期）
- GUI：数据目录旁「选择日期…」，Treeview 每行 ☑ + 点行切换 + 全选/全不选/只选有报告的，
  0 报告的行置灰；全选 → 传 None（= 全部）；换目录重置
- CLI：`--dates` / `--exclude-dates` / `--list-dates`
- 提示：标题日期≠文件夹日期（逐份写日志 + 一条汇总）、本日无报告（列出名字）、
  勾了 include_pending 时写明"加了 N 笔 / +X t"
- `ParsedReport.title_date`、`stats.extra["title_mismatch"]`

### 踩坑

- 标题日期不符是**常态**（83 个文件夹里 12 份），逐条弹警告会刷屏 → 只汇总一条 +
  日志逐份标注。版式上「改了文件名没改标题」不等于数据错。
- `PrintWindow` 截图：WPS/Excel 窗口在前时会挡住 `ImageGrab`，要用
  `win32gui` 找句柄 + `PrintWindow(hwnd, hdc, 2)`。

自检 66 条；真实数据默认全选结果与 v0.4 一致（177 行 / 1,040,953.034 t）。
发版 v0.5，资产 `loss-dilution-tool-v0.5-win64.zip`，回下载 MD5 一致、自检通过。

## 损贫计算工具 v0.6：与人工表的对账（真凶是多表文件）

用户拿 `10月份损失贫化表金斗山分表.xlsx` 对账，3950 差 27,166 t。

**根因（v0.4 埋的）**：现场一天分两次出报告，一个 xlsx 里装两张表——
`3950平台 1006炮孔数据报告`（29,113.973 t）+ `1006-2`（27,166.049 t）。
v0.4 为防 3DMine 附表重复计入，改成"读到合计就停"，把第二份整份丢了。

**改法**：`parser._find_headers()` 把文件按表头切成一张张表，`_read_table()` 逐表读，
`_looks_like_breakdown()` 判断：
- 合计对不上前面任何一行 → 独立报告，照算
- 合计等于前面某一行、或等于前面整表的合计 → 拆分附表，排除
（`_close()` 容差 max(0.01, 0.02%)；1101.776 vs 1101.775 这种四舍五入能对上）
忽略的附表行号 → `report.ignored_rows`，`_block_sources` 遇到就清空 pending，
否则小计会串到下一张表；多表时每份都有自己的「合计」，用 `report.total_rows` 区分。

**对账结果**（北山）：3950 / 3970 / 3990 与人工**完全一致**；3930 南、3940 南 也一致。
其余差异逐条查清：

| 差异 | 结论 |
|---|---|
| 3940 +4,921 | 人工 0930 合计漏了体1（2,060.3，报告自己写 15,421.5）；1018BL 2,860.7 列了明细没进总计 |
| 3960 −4,926 | 人工未列 0919（11,091.2）和 剥离1009（2,366.8）；人工 1009 多 607.6（源文件找不到）；人工把待审 1015（17,776.9）计入了 |
| 3980 −22,723 | 人工有 0815BL，**数据目录里没有这份报告** |
| 4000 −1,959 | 人工有 924-2（3,758.5，目录里没报告）；程序算了 0920（标题写 0825）1,799.5 |
| 3930北 +19,045 | 人工表没有这个平台 |
| 南山 +87,373 | 人工南山页只填了 3 个平台的部分日期（3920 只有 1003） |

**查数据的手法（可复用）**：扫全部 202 个 Excel（含 123 个 .xls）找含「类型/体号」表头的表，
确认 0815BL / 924-2 确实不存在；按重量做贪心配对，把人工的行和程序的报告一一对上。

产出：`对账表_程序vs人工.xlsx`（平台对照 + 逐日对照，差异标黄）在数据目录里。
总量 1,040,953.03 → **1,068,119.08**；自检 70 条（`tests/test_parse_tables.py` 4 条）。
发版 v0.6，资产 MD5 回验一致。

**教训**：v0.4 那种"读到合计就停"的保守修法会误伤多表文件。判断"是不是重复"
必须看内容（合计是否等于前面某行），不能看位置。

## 10:56 用户再问 3940 差 2,060.252 —— 结论：人工表把「小计」当扣减项了

用户拿 `二次圈矿量合计_20261021_1034.xlsx`（v0.6 跑出，且**勾了「把待审数据也计入」**）
对 `10月份损失贫化表金斗山分表.xlsx`，问 北山3940 为什么 231,243.399 vs 229,183.147。

**差 2,060.252，全部来自 3940 平台 0930 这一天的一份报告：**

```
3940平台 0930炮孔数据报告.xlsx
3  1.000-1.500 体1  763.056   2,060.252   1.218   25.089
4  小计               763.056   2,060.252
```

### 做对账工具时踩的坑（_probe/reconcile2.py）

1. **逐日配对的键要用「报告标题里的日期」**，不能只用文件夹名 — 3970 的 0924 文件夹里
   还放着 `3970平台 0923炮孔数据报.xlsx`（文件名还少了个「告」），按文件夹配会合错。
2. **别用 `name.split("-")[-1]` 取日期**：`…-1003 - 2` 会被切成 `2`，整列对不上。
   直接对整个文件夹名做 `canon()`（正则锚定结尾）才对。
3. **一个文件多份报告**（3950 的 1006 里装 1006 + 1006-2）时，程序只能按文件合计，
   要允许「程序一个键 = 人工两三个键之和」的子集配对，否则永远显示差异。
4. 人工南山页：A 列为空的行有两种——平台小计（跳过）和整平台合计（3940 只有一行、
   没拆日期，要收）。用「与上方明细之和是否相等」区分。
5. `剥离1009` 与 `1009` 的键必须分开，否则会合并成一个 11,197.384。

产出 `对账表_程序vs人工_1021.xlsx`（平台对照 / 逐日对照 / 差异桥，差异标黄）。
