## 炮孔报告汇总按矿段换品位分级（v1.13）

### 问题
中心矿段汇总"少一档"：人工成果 `0.500-0.800 / 0.800-1.000 / 1.000-999.000`，
程序出来只有 `0.500-1.000`（0.55 / 0.75 / 0.90 全并进去）。

根因：`excel_tools/src/blast_report/schema.py` 的 `GRADE_BANDS` 写死金斗山五档，
`by_total.collect_total_blocks()` 反推档位时直接调 `band_of_grade(grade)`，与"选的哪个矿段"无关。

### 改法
* 新增 `excel_tools/config/grade_profiles.json`：`edges`（分界值）+ `keywords`（认矿段），
  档位名按 `%.3f-%.3f` 自动生成；`jindoushan` / `center` 两套，`default=jindoushan`。
* 新增 `src/blast_report/profiles.py`：载入/校验（坏配置回落内置并告警）、
  `GradeProfile.band_of()`（左闭右开）、`resolve_profile()`（手动 > 路径关键字 > 源报告档位 > 默认）。
* `schema.band_of_grade(值, 分级)`、`by_total` 收 `profile`、`builder.MergeOptions.grade_profile/grade_config`，
  `merge_reports` 返回里加了 `grade_profile(_name/_reason/_source)` / `grade_bands` / `warnings`。
* CLI `--grades` / `--grade-config`；GUI「汇总方式与品位分级」加矿段下拉框，日志打 `[分级]` + 告警。
* `naming.guess_title()` 顺手修：平台标签已带矿段名（分级配置的 keywords）就不再补"北部山头"。

### 口径
* 边界一律**下限含、上限不含**；相邻档共用分界值 → 不重叠不留缝（自检逐 0.001 扫过）。
* 低于工业品位下限：金斗山（下限 0）贴最低档不变；中心矿段（下限 0.5）单列 `<0.500` 排最后 + 告警。

### 验收
新增 `excel_tools/tests/test_grade_profiles.py` **48/48**（两套分级边界、扫描、识别、同一批数据两套汇总对比、
低于下限、配置容错、真实 3580 报告档位核对）；`test_by_total` 14/14、`test_formats` 25/25、`test_locks` 13/13 未变。
`test_merge` / `test_daily_merge` 依赖 `D:\WK\N CRT\` 真实数据，本机没有 → 按原样跳过。
`_probe/accept_all.py` ⑤ 从 5 项加到 6 项。

实测 3570-1023（总计品位 0.8177）：修复前落 `0.500-1.000`，修复后落 `0.800-1.000`。

## 二次圈矿链路也按矿段换分级（v1.14）

v1.13 只改了报告汇总；圈矿链路（oreblocks/autoblock/strip/deliver/run_batch/merge_to_composite）
还写着金斗山四档，中心矿段 0.85 会被并进 0.5-1。

### 改法
* 新增 `core/grades.py`：档位/识别/图层名/短标签/色号/`order_map()` 的唯一入口，
  读的是**同一份** `excel_tools/config/grade_profiles.json`。
* json 新增 `ore_cutoff`（=0.5）：圈矿的工业品位下限，低于它的档（金斗山 0.000-0.500）
  不进圈矿档位 —— 这样金斗山仍是 L1~L4，老成果不变。
* 删掉 `oreblocks.LEVELS` 常量（import 时固定，换矿段不跟着变，正是出错根源）；
  所有 `("L4",3.0,9e9,…)` 四元组 → `grades.ids_desc()` / `levels_desc()`；`0.5` 废孔阈值 → `grades.cutoff()`。
* 识别：界面「矿段」下拉 > `--grades` > `圈矿参数.json` 的 `mine_section` > 路径关键字 > 默认。
  run_batch 每个单日目录认一次；gui 把选择传给 run_strip / run_batch / merge_to_composite。

### 验证
* `_probe/test_grades.py` **36/36**（含同一批 9 孔在两套分级下真跑 pipeline、真实 3580 数据）。
* **金斗山回归**：3940-1008 前后各跑一遍，报告 12×6 **逐格 0 差异**，`.3ds` 只差文件头路径。
* 中心矿段 3580-1011：块 `1.000-999.000 / 0.800-1.000 / 0.500-0.800`，孔数统计 `≥1/0.8-1/0.5-0.8/<0.5` = 2/2/11/67。
* excel_tools 48/48、by_total 14/14 未受影响。

### 期间遇到的坑
* 仓库 `.git/objects/pack/*.pack` 与 `.git/refs/` 被意外清掉（`git stash push` 之后出现），
  `git status` 报 `not a git repository`。修法：重建 `refs/heads|tags|remotes` 并把 HEAD 指向原提交，
  再 `git fetch origin main` 把对象补回来（部分老 tag 对象仍缺，不影响新提交与 push）。
  → **在这个仓库里别再用 `git stash` 做 A/B**，改用 `git archive HEAD <dir> | tar -x -C 临时目录`。
* 沙箱的安全删除不可用：`shutil.rmtree`/`rm -rf` 会抛 `SAFE_DELETE_FAIL_CLOSED`；
  自检产物清理不掉就留着（`_out`、`release_v1/_v114_check`）。
